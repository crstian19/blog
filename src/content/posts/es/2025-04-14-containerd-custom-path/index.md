K3s guarda todo lo de containerd en `/var/lib/rancher/k3s/agent/containerd`, y ahí lo que más ocupa son las imágenes de los containers. Si el disco del sistema es pequeño se llena antes de lo que parece, así que vamos a ver como moverlo a otro disco, por ejemplo a `/mnt/containerd`.

Todo esto aplica a K3s con containerd 2.0, que viene de serie desde las releases de febrero de 2025 (v1.31.6+k3s1 y v1.32.2+k3s1). Para comprobar qué versión tienes:

```bash
k3s --version
k3s ctr version
```

## Por qué no vale con editar el config.toml

K3s genera el `config.toml` de containerd en `/var/lib/rancher/k3s/agent/etc/containerd/config.toml` y lo vuelve a escribir en cada arranque, así que cualquier cambio que hagas ahí desaparece en el siguiente reinicio. El propio fichero te lo avisa en la primera línea:

```toml
# File generated by k3s. DO NOT EDIT. Use config-v3.toml.tmpl instead.
```

Para personalizarlo, K3s busca una plantilla en ese mismo directorio y la renderiza con `text/template` de Go:

- `config-v3.toml.tmpl` para containerd 2.0, que usa la versión 3 del formato de configuración.
- `config.toml.tmpl` para containerd 1.7, con la versión 2.

Si no encuentra `config-v3.toml.tmpl`, K3s sigue usando `config.toml.tmpl` aunque lleve containerd 2.0. Esto es lo que suele pasar después de actualizar: tenías una plantilla v2 de antes, sigue funcionando y no te enteras de que hay otro nombre.

## El directorio en sí: `root`

En el formato de containerd, `root` (datos persistentes: imágenes, snapshots, contenido) y `state` (sockets y datos de ejecución) son claves de primer nivel, no van dentro de ninguna sección. Por eso esto no funciona:

```toml
[containerd]
  root = "/mnt/containerd"
```

Lo correcto es poner `root = "/mnt/containerd"` arriba del todo. `state` lo dejaría donde está (`/run/k3s/containerd`): es un tmpfs, no ocupa disco y ahí vive el socket que usan `crictl`, `ctr` y cualquier cosa que monte el socket (yo tengo un CronJob en el cluster que hace `nerdctl image prune` contra `/run/k3s/containerd/containerd.sock` y se rompería).

## Opción 1: un drop-in en `config-v3.toml.d` (K3s reciente)

En las versiones recientes de K3s (la v1.36.0 ya lo trae), la plantilla base que genera el `config.toml` incluye una línea `imports` que carga todos los `.toml` de `config-v3.toml.d/`. containerd sobrescribe los campos simples (strings, números) con lo que venga en los ficheros importados, así que basta con:

```bash
sudo mkdir -p /var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.d
sudo tee /var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.d/root.toml <<'EOF'
version = 3
root = "/mnt/containerd"
EOF
```

Es la forma más limpia porque no tocas la plantilla de K3s y te sigue llegando todo lo que cambien en las siguientes versiones. Para saber si tu versión lo soporta, mira si el `config.toml` generado tiene la línea `imports = [".../config-v3.toml.d/*.toml"]`.

## Opción 2: una plantilla completa en `config-v3.toml.tmpl`

Si tu K3s no tiene esa línea `imports`, toca plantilla. Aquí ojo con dos cosas.

La primera: la documentación de K3s recomienda no copiar el `config.toml` ya renderizado a la plantilla y editarlo. Ese fichero tiene los valores de tu nodo ya escritos a fuego (rutas, versión de la imagen de pause, CNI...) y desde ese momento K3s ya no los actualiza. Funciona hoy, pero en la próxima actualización te puede morder.

La segunda: K3s permite extender su plantilla base con `{{ template "base" . }}` y añadir líneas debajo, que es lo ideal para meter un runtime nuevo, por ejemplo. Pero para `root` no sirve, porque la base ya define `root` y TOML no deja repetir una clave: containerd no arrancaría.

Así que para cambiar `root` lo que queda es partir de la plantilla por defecto de K3s (`ContainerdConfigTemplateV3` en [templates.go](https://github.com/k3s-io/k3s/blob/main/pkg/agent/templates/templates.go), de la versión de K3s que tengas instalada) y cambiar solo esta línea:

```toml
root = {{ printf "%q" .NodeConfig.Containerd.Root }}
```

por:

```toml
root = "/mnt/containerd"
```

Y guardarla en `/var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.tmpl`. Al ser una copia de la plantilla, cuando actualices K3s tendrás que revisar si ha cambiado, que es justo lo que te ahorras con la opción 1.

## Opción 3: no tocar containerd

Hay dos formas de mover los datos sin cambiar la configuración de containerd:

- **`--data-dir`** (o `data-dir:` en `/etc/rancher/k3s/config.yaml`): mueve todo `/var/lib/rancher/k3s`, no solo containerd. Tiene sentido en una instalación nueva; en un nodo que ya está funcionando es casi como montarlo de cero.
- **Un bind mount** del directorio nuevo sobre el de siempre. containerd sigue pensando que escribe en `/var/lib/rancher/k3s/agent/containerd` y no hay plantilla que mantener:

  ```bash
  # /etc/fstab
  /mnt/containerd  /var/lib/rancher/k3s/agent/containerd  none  bind  0  0
  ```

  Si el disco nuevo es solo para esto, también puedes montarlo directamente en esa ruta y te ahorras el bind.

La verdad es que para un nodo que ya existe, el bind mount es la opción que menos puede fallar.

## Las imágenes que ya tenías

Cambiar `root` no mueve nada. containerd arranca con el directorio nuevo vacío y vuelve a descargar todas las imágenes que necesiten los pods, y lo viejo se queda ocupando espacio en el disco de antes.

Si no quieres volver a descargarlas (o tienes imágenes importadas a mano que no están en ningún registry), cópialas antes de reiniciar. Primero hay que parar K3s del todo. `systemctl stop k3s` no basta porque K3s deja los containers corriendo al pararse a propósito, y con las capas montadas no puedes copiar de forma fiable. Para eso está el script que instala K3s:

```bash
sudo /usr/local/bin/k3s-killall.sh
sudo rsync -aHAX --numeric-ids /var/lib/rancher/k3s/agent/containerd/ /mnt/containerd/
```

El `-HAX` conserva hard links, ACLs y atributos extendidos, que los snapshots de overlayfs usan. Después aplicas la opción que hayas elegido y arrancas:

```bash
sudo systemctl start k3s   # k3s-agent si es un worker
```

Cuando hayas comprobado que todo funciona, ya puedes borrar el directorio viejo (con la opción del bind mount no lo borres, que es el punto de montaje).

## Comprobar que funciona

Que containerd está usando la ruta nueva:

```bash
sudo k3s crictl info | grep -i rootdir
# "containerdRootDir": "/mnt/containerd",
```

Que las imágenes siguen ahí y el espacio se ha ido al disco nuevo:

```bash
sudo k3s crictl images
sudo du -sh /mnt/containerd
df -h /mnt /
```

Y si has ido por plantilla o drop-in, que K3s la ha cogido: el `config.toml` renderizado tiene que llevar tu `root`.

```bash
grep '^root' /var/lib/rancher/k3s/agent/etc/containerd/config.toml
```

Ojo con este último: con la opción 1 el `root` del `config.toml` sigue siendo el de siempre, porque el cambio llega por el import. Ahí lo que manda es lo que diga `crictl info`.
